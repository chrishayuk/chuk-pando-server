# Releasing pando

Releases are built by GitHub Actions from a tag, created as a **draft**, checked on the bytes actually uploaded, and
only then published. Nothing is published by a push or by the build-and-test workflow.

## Installer integrity: what is verified, and what it means
**There are three different assurances:**
1. **HTTPS transport.** The file came from the named host, unmodified in transit.
2. **A checksum against a digest.** The file matches the SHA-256 computed when the release was built. This catches
   a corrupted, swapped or substituted file. The digest is embedded in the installer that the same release serves,
   so **it is integrity, not independent authentication of the publisher**: whoever can replace files in the
   release can replace the digest too.
3. **An attestation independent of the download location.** Each archive has a GitHub artifact attestation, which
   is Sigstore-signed provenance tying it to this repository's `release.yml`. Check it with `gh attestation verify
   <archive> --repo <owner>/chuk-pando-server`.

**What the installers do** (generated by cargo-dist 0.34, then hardened by `verify/release/patch_installers.py`
before upload):
- **`pando-installer.sh` (macOS, Linux):**
  - checks the archive's SHA-256 against the embedded digest, with `sha256sum`, `shasum -a 256` or
    `openssl dgst -sha256`;
  - **fails closed**: no tool, no digest, or a mismatch means nothing is installed.
- **`pando-installer.ps1` (Windows):** checks the archive's SHA-256 with `Get-FileHash` before unpacking, and
  refuses on a mismatch or a missing digest.
- Neither installer verifies attestations. Users who want publisher authentication run `gh attestation verify`.

**What the tests prove** (`verify/release/installer_test.sh` and `installer_test.ps1`, on every platform):
- a valid install works, and the installed binary passes the smoke test;
- a **corrupted** archive (random bytes) and a **substituted** archive (well-formed, wrong content) are refused for
  their checksum, and nothing is installed;
- on macOS and Linux, the installer refuses when no SHA-256 tool exists, and installs when only `shasum` exists.

These tests prove that integrity checking works and fails closed. They do not prove who published the release.
Only the attestation check does.

## Native tests (`.github/workflows/build-test.yml`)
On each of the five runners (macOS ARM64 and x86-64, Linux x86-64 and ARM64, Windows x86-64), from the packaged
archive:
- the unit tests;
- `verify/release/smoke.py`:
  - serve, port and data locks;
  - **bind refusal without credentials, and Basic auth**;
  - push, clone and fsck;
  - explain and explore;
  - incremental fetch, 8 concurrent branches;
  - hard kill and restart;
- the archive's licence and attribution files;
- the installer tests;
- `verify/release/readme_test.py`, which runs the README's commands literally in a clean profile.

`workflow_dispatch` with `draft_tag` runs the same installer and README tests against a **draft release's uploaded
assets**. It also verifies the checksums and the attestation of every archive.

## What is configured
- **`.github/workflows/release.yml`** (cargo-dist 0.34, tag-triggered). It carries two edits that `dist generate`
  does not produce. `dist-workspace.toml` sets `allow-dirty = ["ci"]` so that `dist` accepts them:
  1. **build-global-artifacts:** `python3 verify/release/patch_installers.py target/distrib` runs right after
     `dist build --artifacts=global`, so the uploaded installers are the hardened ones:
     - the `.ps1` verifies SHA-256;
     - the `.sh` fails closed.
  2. **host:** `gh release create ... --draft`. Nothing is public until `gh release edit --draft=false`.

  After any `dist generate`, check that both edits are still there. `grep -n 'patch_installers\|--draft'
  .github/workflows/release.yml` must show 2 lines.
- **`.github/workflows/build-test.yml`, `workflow_dispatch` with `draft_tag`:**
  1. Asserts the release is still a draft.
  2. Downloads every asset of the draft.
  3. Checks `sha256.sum`, and that the installers are the patched ones.
  4. Runs `gh attestation verify` on every archive, with `--signer-workflow .../release.yml`.
  5. Runs the installer tests and the README-first test natively on the five runners, using those exact
     downloaded assets.

## Preconditions
- The repository is **public**. GitHub does not create artifact attestations for private repositories on a personal
  account, so `release.yml`'s attest step would fail.
- The commit to release has passed the regression gate (`docs/VERIFY.md`) and `build-test.yml`.
- **Two separate approvals are needed:** publishing the source (making the repository public) and publishing the
  binaries (un-drafting the release).

## Steps
```sh
REPO=<owner>/chuk-pando-server
TAG=v0.1.0
COMMIT=<the approved commit on main>

# 0. the approved commit passed the gate and build-test.yml
git log -1 --format=%H "$COMMIT"
gh run list -R "$REPO" --workflow build-test.yml --commit "$COMMIT"      # must show success

# 1. tag and push (this starts release.yml: plan, build x5 + attest, global + patch, draft release)
git tag -a "$TAG" -m "pando 0.1.0" "$COMMIT"
git push origin "$TAG"
gh run watch -R "$REPO" "$(gh run list -R "$REPO" --workflow release.yml -L1 --json databaseId -q '.[0].databaseId')"

# 2. the release exists as a DRAFT with every asset
gh release view "$TAG" -R "$REPO" --json isDraft,assets -q '.isDraft, (.assets[].name)'
#    expect: true; 5 archives + 5 .sha256, pando-installer.sh, pando-installer.ps1, sha256.sum, source.tar.gz(+.sha256)

# 3. local checks on the uploaded bytes (this Mac)
D=$(mktemp -d); gh release download "$TAG" -R "$REPO" -D "$D"
(cd "$D" && sed 's/ \*/  /' sha256.sum | shasum -a 256 -c)
grep -c 'pando release patch' "$D/pando-installer.sh" "$D/pando-installer.ps1"          # 1 and 1
for f in "$D"/pando-*.tar.xz "$D"/pando-*.zip; do
  gh attestation verify "$f" --repo "$REPO" --signer-workflow "$REPO/.github/workflows/release.yml" || echo "FAIL $f"
done
sh verify/release/installer_test.sh "$D" 18741                 # disposable HOME; macOS ARM64
python3 verify/release/readme_test.py --artifacts "$D" --port 18085

# 4. native checks on all five platforms, against the draft's own assets
gh workflow run build-test.yml -R "$REPO" --ref main -f draft_tag="$TAG"
gh run watch -R "$REPO" "$(gh run list -R "$REPO" --workflow build-test.yml -L1 --json databaseId -q '.[0].databaseId')"
#    must show: fetch-draft (attestations, checksums, patched installers), install-test x5, README-first x5: success

# 5. ONLY with the maintainers' explicit approval: publish
gh release edit "$TAG" -R "$REPO" --draft=false --latest

# 6. after publication: the README as written, with no substitutions, on this Mac and from a clean runner
python3 verify/release/readme_test.py --public --port 18085
curl -fsSI "https://github.com/$REPO/releases/latest/download/pando-installer.sh" | head -1     # HTTP/2 302
```

## If any check fails before publication
```sh
gh release delete "$TAG" -R "$REPO" --yes             # deletes the draft; nothing was public
git push --delete origin "$TAG"
git tag -d "$TAG"
```
Fix the problem on a branch, run the gate and `build-test.yml` again, and start over at step 0 with a new commit.
Reuse the same tag only if it was never published.

## What each check establishes
- **`sha256.sum`:** the uploaded archives are the ones the release run built (integrity within the release).
- **`gh attestation verify ... --signer-workflow`:** each archive was built by this repository's `release.yml`,
  signed through GitHub's Sigstore instance. This is independent of where the file was downloaded from.
- **The installer tests on the draft's assets:**
  - the hardened installers install the genuine archive;
  - they refuse a corrupted archive and a substituted one;
  - the shell installer refuses to install without a SHA-256 tool.
- **README-first:** a new user following the README literally succeeds on each platform, with the release's own
  bytes.
